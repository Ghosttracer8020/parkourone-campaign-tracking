<objective>
Deliver the first-touch UTM attribution bridge: a small consent-gated client capture
(`assets/js/pot-attribution.js`) that parses `utm_campaign/source/medium` + `landing_path` from
the URL, holds them in `sessionStorage` until `analytics` consent is granted, then promotes them
into a first-party `pot_attribution` cookie (first-touch wins, 90-day, SameSite=Lax) — plus the
server bridge (`includes/class-pot-attribution.php`) that, at `woocommerce_checkout_create_order`,
reads the cookie and persists sanitized values into order meta `_pot_campaign/_pot_source/_pot_medium/_pot_landing`.

Purpose: Persisting cookie→order-meta at checkout-create time gives `POT_Conversion::record_conversion`
(plan 01) a STABLE order-meta source to attribute the booking — the conversion handler may fire days
later on a status change and must not depend on a transient cookie. This closes the end-to-end
UTM → cookie → order-meta → booking.campaign chain.

Output: `assets/js/pot-attribution.js` (new), `includes/class-pot-attribution.php` (new), both wired
into `pot_init()` and the require chain. Covers ATTRIB-01, ATTRIB-02, and completes ATTRIB-03 (the
first-touch campaign string is what `aggregate_by_campaign` groups all stages by).
</objective>

<phase_goal>
**As a** ParkourONE marketer, **I want to** have a booking's originating campaign captured first-touch
and carried from the landing URL into the order, **so that** each completed Probetraining booking is
attributed to the campaign that actually produced it — and consent is honored (no cookie before consent).
</phase_goal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `pot_attribution` cookie | Client-controlled cookie value; an attacker can set arbitrary JSON. Must be treated as untrusted input on the server. |
| `$_COOKIE['pot_attribution']` → order meta | Untrusted cookie content crosses into persisted WooCommerce order meta and later into the events store via plan 01. |
| Front-end UTM URL params → JS | URL query is attacker-controllable; values only stored client-side as labels, never executed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-05 | Tampering / Injection | Untrusted `pot_attribution` cookie content written to order meta | mitigate | `json_decode` + `is_array` guard + `sanitize_text_field` + length-cap (substr 100) on EVERY field before `update_meta_data`. Never `eval`/echo raw cookie. Verified by Task 2 grep gates. |
| T-02-06 | Tampering | Bypassing the parameterized store / unsanitized data reaching `wp_pot_events` | mitigate | Attribution writes only to order meta via HPOS CRUD; the booking insert (plan 01) goes through `POT_Store::insert_event` parameterized gateway. Sanitized at the boundary here. |
| T-02-07 | Information Disclosure / Privacy | PII stored in the attribution cookie/meta | mitigate | Only campaign/source/medium/landing labels + first_seen timestamp stored — no names, email, IP. Cookie not HttpOnly is acceptable (no secret; carries only labels). 90-day lifetime documented; DPO review flagged (STATE.md), non-blocking. |
| T-02-08 | Repudiation (consent) | Writing a tracking cookie before analytics consent (TTDSG §25) | mitigate | Cookie written ONLY after `window.poConsent.categories.analytics` is true; UTM held in sessionStorage until then; no consent-change event so next-pageload re-check promotes. Admins skipped entirely. (Pitfall 7.) |
| T-02-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this plan (vanilla JS asset + PHP against existing WP/WC APIs). No supply-chain surface. |

No HIGH-severity unmitigated threats. The cookie-content threat (T-02-05) is the central one and is fully mitigated by decode-guard + sanitize + length-cap at the server boundary.
</threat_model>
