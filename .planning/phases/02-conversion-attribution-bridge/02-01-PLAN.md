<objective>
Deliver the consent-independent, server-side Probetraining conversion listener: a single
`POT_Conversion::record_conversion($order_id)` handler registered on BOTH the primary
`woocommerce_order_status_probetraining` action and the `woocommerce_order_status_changed`
fallback (free/100%-coupon path), guarded by an order-meta idempotency flag so every booking
is counted exactly once. Includes graceful degradation when the `probetraining` status or
WooCommerce itself is unavailable.

Purpose: This is the irreplaceable core-value metric — "if all else fails, the conversion count
must be correct." Server-side and consent-independent so it never depends on the consent banner
or the client funnel.

Output: `includes/class-pot-conversion.php` (new), `POT_Conversion::init()` wired into
`pot_init()`, and the require chain extended. Covers CONVERT-01..04. ATTRIB-03/04 are realized
here because the booking row carries the first-touch campaign read from order meta (written by
plan 02) and empty campaign falls into the existing `POT_Store::UNATTRIBUTED` bucket — bookings
are never dropped.
</objective>

<phase_goal>
**As a** ParkourONE marketer, **I want to** have every completed Probetraining booking counted
exactly once on the server regardless of consent, **so that** the campaign conversion number is
trustworthy even when the client-side funnel or consent banner fails.
</phase_goal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WooCommerce order meta → events store | Conversion reads `_pot_*` order meta (written elsewhere) and writes a booking row. Order meta is set by the plugin/checkout, not directly by an external untrusted actor here. |
| ab-webhook-endpoint dependency → conversion availability | The `probetraining` status is registered by a separate plugin; its absence must degrade, not fatal or silently zero. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering / Repudiation | `record_conversion` double-fire (both hooks + repeated transitions) | mitigate | Idempotency: `_pot_conversion_tracked` meta checked BEFORE insert; verified by ordering assertion in Task 2. Prevents inflated conversion counts (core-value integrity). |
| T-02-02 | Denial of Service / Info | `ab-webhook-endpoint` inactive → silent zero conversions | mitigate | Status detected via `get_post_status_object`; `pot_conversion_status='not_configured'` + dismissible admin notice; fallback hook still registered. Never fatal, never silent zero (Pitfall 6). |
| T-02-03 | Tampering | Writing to `wp_pot_events` outside the parameterized gateway | mitigate | All writes go through `POT_Store::insert_event` (Phase-1 parameterized `$wpdb->insert` with explicit formats). Plan adds NO direct `$wpdb` access. |
| T-02-04 | Information Disclosure | `event_ref` / order data leaking PII into the events store | accept | Only `(int) _event_id` and campaign labels are stored; no names/birthdates copied. event_ref is best-effort int, null otherwise. Low risk, no PII surface. |
| T-02-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this plan (pure PHP against existing WP/WC APIs). No supply-chain surface introduced. |

No HIGH-severity unmitigated threats. Capability checks are not relevant (no new admin write surface; the admin notice is read-only output).
</threat_model>
