<objective>
Harden the walking skeleton from Plan 01 with the operational lifecycle: a daily retention cron that prunes only raw visit/click rows older than the retention window (never booking rows), full uninstall cleanup (drop table + delete options + clear cron), and the GitHub self-updater wired against `monkeyspk/parkourone-campaign-tracking`. The updater is a verbatim copy of the sibling-plugin updater with four value changes and the shared token. This makes the plugin maintainable (self-updates), bounded (retention), and clean (uninstall leaves no orphaned data).

Purpose: A high-volume events store that never prunes bloats the DB and slows date-range queries (Pitfall 10); leaving the table/options/cron behind on uninstall is a data-minimization and hygiene failure (Pitfall 8, "Looks Done But Isn't" uninstall item). The self-updater is the expected delivery mechanism for every monkeyspk plugin.

Output: `includes/class-pot-cron.php`, `includes/github-updater.php`, `.git-version`, `uninstall.php`; edits to `parkourone-campaign-tracking.php` (add the github-updater require LAST + schedule cron on activation + clear cron on deactivation) and `includes/class-pot-plugin.php` (wire `POT_Cron::init()`). Covers INFRA-03, INFRA-05.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WordPress → github.com (api.github.com) | outbound HTTPS GET for update checks (admin-only, throttled) |
| WP-Cron scheduler → prune handler | server-side scheduled DELETE on the events table |
| uninstall request → DB / options / cron | destructive cleanup, runs only under WP_UNINSTALL_PLUGIN |

> Phase 1 still has NO public input surface. The updater is admin-only (constructor returns if !is_admin) and reuses the audited sibling pattern verbatim. The prune and uninstall paths are trusted server-side operations.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Tampering (SQL injection) | POT_Store::delete_raw_older_than | mitigate | The prune DELETE uses `$wpdb->prepare` with a `%s` placeholder for the cutoff; `event_type IN ('visit','click')` is a fixed literal. No variable concatenation. |
| T-01-07 | Tampering (data loss) | prune handler | mitigate | DELETE is constrained to `event_type IN ('visit','click')` so booking rows (business record) are never removed; verified by the seeded smoke test (200-day-old booking survives). |
| T-01-08 | Information disclosure (secret in logs) | github-updater.php | accept | Copied verbatim from the audited sibling updater; it logs bracketed diagnostics but the GitHub token is read from an option, not logged. No NEW secret is introduced this phase (the pull-API Bearer secret lands in Phase 5 with its own redaction handling). |
| T-01-09 | Tampering (supply chain) | github self-update | accept | Update source is the trusted monkeyspk org over HTTPS with the shared token; this is the established, signed-off delivery mechanism for all sibling plugins. No new packages installed (pure PHP, no Composer runtime deps). |
| T-01-10 | Information disclosure (orphaned data) | uninstall.php | mitigate | Uninstall drops the table, deletes all pot_* options, and clears the cron under the WP_UNINSTALL_PLUGIN guard — no orphaned PII-adjacent data remains (Pitfall 8 / Datensparsamkeit). |
</threat_model>
