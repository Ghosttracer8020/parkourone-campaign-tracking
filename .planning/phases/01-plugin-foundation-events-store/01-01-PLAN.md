<objective>
Build the Walking Skeleton for the ParkourONE Campaign Tracking plugin: the thinnest end-to-end path that proves the full foundation stack works. On activation the plugin creates the custom `{$wpdb->prefix}pot_events` table via `dbDelta` (with the three required indices), the `POT_Store` single-gateway class can insert one event row and read it back through `aggregate_by_campaign()`, and a placeholder admin page renders under the existing `parkourone` menu. The bootstrap mirrors the sibling-plugin house style 1:1 and declares WooCommerce HPOS compatibility. The plugin must activate without a fatal even when WooCommerce and `ab-webhook-endpoint` are inactive.

Purpose: Every later phase (conversion tracking, client capture, dashboard, pull-API) reads and writes through `POT_Store` and hangs UI off the `parkourone` admin menu created here. This is the architectural backbone — get the bootstrap, table schema, store gateway, and admin shell right once.

Output: `parkourone-campaign-tracking.php` (main bootstrap), `includes/class-pot-plugin.php`, `includes/class-pot-activator.php`, `includes/class-pot-store.php`, `includes/class-pot-admin.php`, `.gitignore`. Covers INFRA-01, INFRA-02, INFRA-04.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| activation/admin request → custom DB table | WordPress writes the `pot_events` schema and rows via $wpdb |
| admin browser → admin page render | only capability-gated admins should reach the page |
| WordPress ↔ WooCommerce (optional) | HPOS declaration runs only if WooCommerce/FeaturesUtil is present |

> Phase 1 has NO public input surface (no REST routes, no front-end beacon, no untrusted client input). The events table is populated only by trusted server-side calls this phase. Threat surface is intentionally minimal; the client ingest/pull-API threats land in Phases 3 and 5.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering (SQL injection) | POT_Store::insert_event / aggregate_by_campaign | mitigate | All writes use `$wpdb->insert` with an explicit `$formats` array; the aggregate read uses `$wpdb->prepare` with `%s` placeholders for the date bounds. No variable is concatenated into SQL. Never use the `===` / raw-concat anti-patterns flagged in STACK.md. |
| T-01-02 | Information disclosure | class-pot-admin render_page | mitigate | Submenu registered with capability `manage_options`; `render_page()` re-checks `current_user_can('manage_options')` before output. Placeholder page exposes no data. |
| T-01-03 | Elevation of privilege | admin page slug | accept | Page is registered under WP's own capability system; no custom nonce/AJAX this phase (none added until Phase 4). Low risk — read-only placeholder. |
| T-01-04 | Denial of service (DB bloat) | pot_events table | mitigate | Composite indices `(event_type,created_at)` + `(campaign,created_at)` created on activation so date-range GROUP BY hits an index (Pitfall 10); retention pruning lands in Plan 02 (INFRA-05). |
| T-01-05 | Information disclosure (PII / Datensparsamkeit) | pot_events schema | mitigate | Schema deliberately has NO `ip` and NO `user_agent` column (Pitfall 8 / STACK.md). `session_id` is pseudonymous only. No participant data stored. |
</threat_model>
