# ParkourONE Campaign Tracking — Verifizierte Codebase-Befunde

> Quelle: paralleler Verstehens-Workflow (6 Agents, alle Aussagen mit Datei-Belegen). Stand: 2026-05-31.

## Nutzer-Entscheidungen (verbindlich)

- **Datenquelle:** Neues Tracking ERSETZT das bestehende Theme-Analytics-System. Gute Ansätze daraus übernehmen (Consent-Gate, Session-ID, Selektor, Conversion-Hook, Tabellen-Schema-Idee). Theme-Tracker danach deaktivieren (Doppelzählung vermeiden).
- **Kampagnen-Attribution:** UTM First-Touch — utm_campaign/source/medium beim Erstbesuch in Cookie, beim Checkout als Order-Meta persistieren.
- **Übertragung an Statusbord:** Pull-API — Plugin stellt gesicherten Lese-Endpoint bereit; Statusbord-Cron zieht (passt zum vorhandenen Snapshot-Pull-Modell).
- **Datenformat:** Aggregierte Kennzahlen pro Kampagne & Zeitraum (Visits, Klicks, Buchungen, Conversion-Rate).

Do NOT carry over the dead update-manager.php or version.txt.

No in-house charting library exists.
- There is NO existing outbound webhook code to inherit: no wp_remote_post/wp_remote_request anywhere; only wp_remote_get in github-updater.php. Outbound push + signing must be built from scratch.
- The reusable outbound template is settled: copy github-updater.php's wp_remote_get pattern (Bearer Authorization header, timeout, sslverify-fallback, is_wp_error + response-code check + bracketed-prefix error_log) and adapt to wp_remote_post with Content-Type application/json, wp_json_encode body, timeout ~15.

- House storage strategy is settled: WP options (single prefixed array per feature) + post meta (_<prefix>_*); NO custom DB tables exist (no dbDelta/CREATE TABLE in either sibling plugin). A custom table would be a deliberate deviation requiring sign-off.

Guard double-counting with an order meta flag (e.g. _<prefix>_conversion_tracked).

The new plugin must defer hook registration to plugins_loaded and degrade gracefully if that plugin is absent.
- Conversion-time identifiers are settled and available from order-item meta: _event_id (event CPT), _event_product_id, _event_date, _event_title_clean, _event_venue, _event_coach, _event_course_id, _event_participant_data, _event_is_workshop; plus order_id and order total. Registration deferred to plugins_loaded and degrades gracefully if ab-webhook-endpoint (which registers the status) is inactive.

ATTRIBUTION BRIDGE: capture first-touch utm_source/medium/campaign + landing page_url in a cookie on first visit; persist them (plus the theme's po_analytics_session_id) as order meta via woocommerce_checkout_create_order / woocommerce_checkout_update_order_meta, so bookings join back to the originating campaign/landing page — closing the gap that no order<->campaign link exists today.

STORE: a custom dbDelta table wp_<prefix>_events(id, event_type[visit|click|booking], campaign, landing_url, order_id, event_id, session_id, created_at) is the natural fit for date-range queries at visit/click volume (a deliberate, sign-off-gated deviation from the options-only house style); alternatively reuse the theme's wp_po_analytics_events table. Plugin inbound REST route(s) for visit/click use a real permission_callback (wp_rest nonce), never __return_true.

DASHBOARD: add_submenu_page('parkourone', ...) cap manage_options, rendered in <div class=\"wrap\"><h1> with the nav-tab-wrapper pattern; a date-range picker drives $wpdb queries grouped by campaign; results shown in plain <table class=\"wp-list-table widefat fixed striped\"> rows (sprintf + esc_*), refreshed via wp_ajax_<prefix>_* + check_ajax_referer + cap check + wp_send_json_*. Assets gated on parkourone_page_<slug>. No in-house chart lib exists (introduce one only if charts are required).

OUTBOUND WEBHOOK to ONE Statusboard (the only side built here): a sender adapted from github-updater.php's wp_remote_get pattern -> wp_remote_post($endpoint, ['headers'=>['Content-Type'=>'application/json','Authorization'=>'Bearer '.$secret], 'body'=>wp_json_encode($payload), 'timeout'=>15, 'blocking'=>false]) with is_wp_error + response-code check + bracketed-prefix error_log('[POT Tracking] ...') and last-send status persisted to an autoload=false option for admin health display. Payload uses camelCase fields and a generatedAt ISO timestamp to fit the Snapshot/passthrough contract; the secret lives in a dedicated option (generated via wp_generate_password(32,false) on activation if needed), NOT wp_salt. Recommended trigger: push booking conversions near-real-time (blocking=>false) and a batched periodic aggregate of visits/clicks via wp_schedule_event; optional HMAC-SHA256 body signature using hash_hmac+hash_equals for stronger auth. The Statusboard receiver route (Next.js Route Handler mirroring /api/cron/refresh auth) is out of scope for this build.

## Risiken

- Double-counting: the theme's analytics-tracker.js already emits cta_click (regex includes 'probetrain'/'buchen') and add_to_cart. A parallel plugin JS listener on the same buttons will double-count and may conflict; must either dedupe, reuse window.poTrack/data-po-track, or rely on server-side hooks for conversions.
- DSGVO/consent: the repo has a consent manager + SECURITY-REVIEW.md and the existing tracker is gated on po_has_consent('analytics') and excludes admins. Client-side visit/click tracking that ignores this gate is a privacy violation; UTM/landing cookies and session bridging also touch consent scope.
- Dependency coupling: the 'probetraining' order status only exists when ab-webhook-endpoint is active (AB_Custom_Statuses). If it is deactivated or load order differs, the woocommerce_order_status_probetraining hook never fires and conversions silently drop to zero; needs graceful degradation and a fallback on order_status_changed.
- Free/100%-coupon Probetrainings may bypass woocommerce_payment_complete and only reach the status via the ab_redirect_order_to_event_status fallback (woocommerce_order_status_completed/processing at priority 999) — relying on a single hook will miss these bookings.
- No existing queue/retry/idempotency for outbound pushes; wp_remote_post with blocking=>false is fire-and-forget. On Statusboard downtime or network errors, events are lost unless a retry/re-queue (wp_schedule_single_event) and idempotency key are added — entirely new code.
- Custom DB table is a deliberate deviation from house style (no dbDelta exists in either sibling). High visit volume without indexing/retention/pruning can bloat the DB and slow date-range queries; needs indices on (event_type, created_at, campaign) and a retention policy.
- Attribution accuracy: without persisting session_id/UTM as order meta at checkout, bookings can only be joined to campaigns via same-day visitor_hash heuristics (the current weak get_probetraining_count approach), undercounting/misattributing conversions.
- Statusboard contract drift: there is no inbound receiver yet, so the payload shape is unverified against a live endpoint. If the future Snapshot mapping differs, pushed fields may be ignored (passthrough) and silently never displayed; the WP and Statusboard sides must agree on the secret, header, and event/snapshot shape before go-live.
- Selector fragility: a[href*="/probetraining-buchen"] is robust today but depends on the URL never changing; stundenplan-detail also emits /probetraining-buchen/?event=ID variants which the *= match catches but query-param noise could complicate de-duplication of which CTA was clicked.
- Charts: no in-house charting library exists. If the dashboard needs visualizations, adding Chart.js/ApexCharts (CDN vs bundled) is an unmade decision with its own privacy (CDN) and maintenance implications.

## Detail-Befunde je Bereich

### WordPress plugin "AB Webhook Endpoint" — REST registration & outbound HTTP patterns (for a new event-pushing tracking plugin)

This plugin is an INBOUND webhook RECEIVER, not a sender. It registers WooCommerce-order REST endpoints under namespace `ab/v1` (includes/class-ab-rest-endpoint.php) that an external "Academy Board" calls to update order statuses. CRITICAL for the new tracking plugin: every REST route uses `permission_callback => '__return_true'` — i.e. NO authentication at all on the REST layer. There is NO outbound webhook code: no `wp_remote_post` or `wp_remote_request` exists anywhere in the plugin. The only outbound HTTP is `wp_remote_get` in the GitHub auto-updater (includes/github-updater.php), which DOES show a reusable pattern: Bearer-token Authorization header, timeout, sslverify fallback, and `is_wp_error` + `error_log` handling. HMAC (`hash_hmac('sha256', ...)`) is used only to generate/verify per-order PDF-download tokens (includes/helper-functions.php), not to sign any outbound payload. So the new plugin must BUILD outbound push + signing from scratch; this codebase only offers a Bearer-auth GET pattern and an HMAC-token verification pattern to mirror, plus a clear example of what NOT to do (open `__return_true` endpoints).

**Wiederverwendbare Muster:**

  - ↻ Mirror the static-class + `rest_api_init` hook + `register_rest_route('<ns>/v1', ...)` structure. For a tracking plugin that PUSHES events you likely won't need inbound routes at all, but if you add a config/health endpoint, copy the `validate_callback` arg pattern. - **permission_callback / auth scheme — INSECURE, do not copy** (`includes/class-ab-rest-endpoint.php:16,23,37,44,51`): Every single route sets `'permission_callback' => '__return_true'`. ### WordPress plugin "house style" (ParkourONE / monkeyspk sibling plugins: ab-webhook-endpoint + custom-events-plugin)

Both plugins follow a consistent, hand-rolled (no Composer autoload for plugin code, no framework) WordPress plugin convention authored by "Pierre Biege" under the GitHub org `monkeyspk`. The main file lives at plugin root, declares a standard plugin header (Version as a bare number like 1.4 / 1.7), guards with `if (!defined('ABSPATH')) exit;`, then linearly `require_once`/`include_once`-loads every class from `includes/`, and wires them up in a single `*_init` function hooked on `plugins_loaded`. Classes use a one-class-per-file convention named `class-<prefix>-*.php` and are either static-init (`Class::init()` registering `add_action('admin_menu'/'admin_init', ...)`) or `new Class()`. ab-webhook-endpoint uses the strict `AB_` class prefix + `ab_`/`ab-` option/slug prefix; custom-events-plugin uses `Event_`/`event_`/`custom_events_` prefixes. All admin pages hang off a shared top-level menu slug `parkourone` (owned by the parkourone theme, NOT created by these plugins) via `add_submenu_page`, gated by `current_user_can('manage_options')` (or `manage_woocommerce`), with WP Settings API (`register_setting`/`add_settings_*`/`settings_fields`) for options pages and ad-hoc `<form method="post" action="options.php">` rendering. Data is stored exclusively in WP options (single array per feature, e.g. `ab_gutschein_settings`) and post meta on CPTs — there are NO custom DB tables (no dbDelta/CREATE TABLE anywhere). No JS charting library is used at all. Self-update is via a per-plugin `includes/github-updater.php` (class `<Prefix>_GitHub_Updater`, instantiated at file end) that polls `api.github.com/repos/monkeyspk/<slug>/commits/main`, compares the 7-char SHA against a local `.git-version` file, downloads the zipball and self-overwrites — this is the expected mechanism for new plugins. The root `update-manager.php` is dead legacy code (never instantiated).

**Wiederverwendbare Muster:**
- **Main-file bootstrap header + require pattern** (`ab-webhook-endpoint/ab-webhook-endpoint.php:1-150 ; custom-events-plugin/custom-events-plugin.php:1-46`): Plugin lives in a root file matching the folder slug. Header block (lines 2-8 / 2-7): `Plugin Name`, `Description`, `Version: 1.4` (bare number, not semver-with-v), `Author: Pierre Biege`, optional `Text Domain`. Immediately `if (!defined('ABSPATH')) { exit; }`. Then a flat list of `require_once plugin_dir_path(__FILE__) . 'includes/class-ab-*.php';` (ab) / mixed `include_once`+`require_once` (cev). A single init function `ab_we_init_plugin()` / `custom_events_plugin_init()` calls `Class::init()` or `new Class()` for every module, hooked via `add_action('plugins_loaded', 'ab_we_init_plugin', 11)` (ab uses priority 11) / `add_action('plugins_loaded', 'custom_events_plugin_init')`. Activation/deactivation via `register_activation_hook(__FILE__, 'ab_we_on_activate')` which calls `flush_rewrite_rules()`. github-updater.php is the LAST require.
  - ↻ New plugin: root file `<slug>.php` with identical header (Author: Pierre Biege, Version as bare number). ABSPATH guard, flat `require_once includes/class-<prefix>-*.php` list ending with `includes/github-updater.php`, and one `<prefix>_init()` on `plugins_loaded` that instantiates each module. ### Probetraining booking conversion — server-side event model for tracking plugin

Booking is 100% WooCommerce-based. Events are a custom post type ('event', registered in custom-events-plugin), but each event DATE is synced to a real WooCommerce simple product (Event_Dynamic_Product_Handler), added to the cart via $_POST['event_id'], and checked out as a normal WC order. A COMPLETED Probetraining booking is therefore a WC_Order whose status is the CUSTOM status 'probetraining' (slug 'wc-probetraining'). That status is NOT set by the custom-events-plugin itself — it is set by the companion plugin Input/ab-webhook-endpoint on the woocommerce_payment_complete hook (check_and_set_probetraining_status), which detects an event booking and maps the event category to a status. The cleanest single conversion hook to count a real Probetraining conversion is woocommerce_order_status_probetraining (fires when the order enters that status). Probetraining is distinguished from Workshop/Kurs because per-date products and the 'probetraining' event_category slug only apply to events that are neither is_workshop nor is_course; workshop/kurs orders land in 'workshop'/'kurs' statuses instead. Note: the parkourone-theme ALREADY has a server-side purchase tracker (woocommerce_checkout_order_processed -> track_purchase) but it does NOT distinguish event type and records no order/product/event IDs — that is the gap the new tracking plugin should close.

### ONE Statusboard — dashboard stack & data-ingest architecture (for aligning a new WP plugin's outbound webhook)

The dashboard is a Next.js 16 App Router app (React 19, TypeScript, Tailwind 4) deployed on Vercel (project "one-statusboard", prj_WrofcoY2reW6CKsl7WkRwTWSaeWZ), with a standalone/Docker build option. CRITICAL FINDING: the dashboard is PULL-based, not push-based — it has NO inbound webhook/ingest receiver that accepts an external POST body.
